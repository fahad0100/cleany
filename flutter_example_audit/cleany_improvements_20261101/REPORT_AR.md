# نتائج تحسين CLEANY

تم تنفيذ التحسينات داخل أداة CLEANY وقوالبها واختباراتها. لم تُستبدل ملفات مشروع المتجر الأصلي؛ نُفّذ اختبار الترقية على نسخة مؤقتة منه. بقي رقم الإصدار الحالي كما هو، وسُجلت التغييرات تحت Unreleased في CHANGELOG إلى حين تجهيز إصدار جديد.

**Doctor**

- يعتمد على العقود المسجلة للميزات المعروفة، فلا يحاول فرض الأنواع المسطحة على Models المخصصة.
- يحافظ على الملفات المعدلة، ويستكمل تشخيص بقية المشروع عند اكتشاف عقد غير مسجل لا يستطيع استنتاجه.
- يعرض العقود غير المدعومة كتشخيص يحتاج مراجعة، دون تخمين مخطط بديل أو تغيير بيانات المستخدم.
- نجح الفحص والتطبيق والتحقق على نسخة المتجر ذات Models المتداخلة.

**إضافة Use Case واختيار Entity**

- عند اختيار نتيجة Entity يظهر اسم Entity الخاصة بالميزة افتراضيًا؛ Enter يحتفظ بها.
- يمكن كتابة اسم Entity أخرى موجودة داخل Domain، أو مسار مصدرها داخل lib عند تكرر اسم الفئة.
- يستخدم النوع المختار في عقد Repository والتنفيذ وUse Case وحالة Cubit/Bloc، مع الاستيرادات اللازمة.
- لا تنشئ الأداة Entity بديلة ولا تعيد كتابة Model أو Entity الموجودة.
- إذا أمكن التحويل المباشر بين الحقول يُحتفظ به. عند اختلاف الأشكال تُنشأ دالة تحويل مكتوبة النوع داخل Data يكملها المطور؛ لا يتوقف التوليد ولا تُضاف تحويلات قسرية.
- تبقى نقطة Backend واضحة وغير موصولة حتى ينفذها المطور. يظل Failure هو نتيجة العملية غير الموصولة بدل نجاح تجريبي زائف.
- تُحفظ هوية Entity المختارة في السجل، وتُستخدم عند الإصلاح، وتُحدّث عند نقل أو إعادة تسمية الميزة التي تحتويها.

**الأنواع**

المدخلات المدعومة:

```text
string
int
double
bool
datetime
list
list<string>
list<int>
list<num>
list<map<string,dynamic>>
map<string,dynamic>
set
dynamic
dynamicic
```

`dynamicic` اسم بديل يُحوّل إلى النوع الصحيح `dynamic`. تصبح list وset من النوعين List<dynamic> وSet<dynamic>. تُوحّد حالة الأحرف والمسافات، وتعمل nullable للأنواع المركبة. النوع dynamic يقبل null أصلًا ولا يُنتج dynamic? غير الصالح. احتُفظ بدعم list<int> السابق.

اختبارات Flutter الفعلية تتحقق من توليد Freezed وJSON، وتحويل القوائم والخرائط والمجموعات، وDateTime والقيم nullable وdynamic، ثم وصول البيانات إلى Entities.

**السرعة والأمان**

توجد ذاكرة مؤقتة محلية لحالة المترجم وbuilder في `.cleany/cache/validation`. تُحدّث مصادر المشروع ومدخلاته في كل عملية، وتظل أوامر الحزم والبناء والتحليل تعمل قبل التطبيق. لا تطبق الأداة الملفات مباشرة من ذاكرة المصدر المؤقتة دون تحقق.

تُلغى الذاكرة عند تغير هوية SDK أو فشل التحقق أو انقطاع تجهيزها. تنظيف Cache من قائمة الصيانة يزيل الذاكرة المملوكة للأداة مع حفظ نسخ الاستعادة والـCaches العامة.

المقارنة الأخيرة بين عمليتي إنشاء مكوّن دون حالة متكافئتين، الأولى بعد مسح Cache والثانية مع إعادة استخدامها:

| المزود | تحقق بارد | تحقق لاحق دافئ |
| --- | --- | --- |
| Dio | 25.765 ثانية | 9.599 ثانية |
| Retrofit | 48.542 ثانية | 9.521 ثانية |

هذه أرقام محلية تشمل الحزم والبناء والتحليل والإدخال/الإخراج؛ تتأثر بالشبكة وحمل الجهاز ولا تمثل ضمانًا لكل مشروع. لم تُقَس ذاكرة RAM أو مشاريع ضخمة. التحسن الثابت وظيفيًا هو إعادة استخدام حالة المترجم والبناء مع المحافظة على التحقق الكامل.

**النكهات والمنصات**

كشف البناء الفعلي مرجع أيقونات AppIcon-dev/uat/prod غير الموجودة عند عدم تشغيل مولدات الأصول. جرى تعديل إعداد التنفيذ ليستخدم AppIcon الموجودة في المشروع عندما لا توجد أيقونة أو إعداد صريح من المطور. تُحفظ الأيقونات والإعدادات المخصصة.

| المنصة | dev | uat | prod | نطاق التحقق |
| --- | --- | --- | --- | --- |
| Android | نجح | نجح | نجح | APK فعلي، وفحص application ID من الملفات الناتجة |
| iOS | نجح | نجح | نجح | بناء Simulator وتشغيل كل نكهة، وفحص معرفات التطبيقات المثبتة |
| macOS | نجح | نجح | نجح | بناء تطبيق فعلي لكل نكهة |

تحققت معرفات Android وiOS من وجود .dev و.uat مع بقاء prod على المعرف الأساسي. الأدلة التفصيلية في native_identifiers.json. هذه عمليات بناء Debug؛ لا تعني إنشاء إصدارات متاجر موقعة. لم يُنفّذ اختبار واجهة على جهاز Android في هذه الجولة.

أضيفت وظائف CI مستقلة للبناء الفعلي للنكهات الثلاث على Android وiOS وmacOS، إلى جانب مصفوفة اختبارات المولد الموجودة.

**نتائج الاختبارات**

- تحليل مصادر الأداة: لا توجد ملاحظات.
- التنسيق وفحص اختلافات Git: سليم.
- اختبارات الأداة الافتراضية: 182 ناجحة. اختبارات التكامل الاختيارية شُغلت منفصلة.
- مصفوفة التطبيقات المولدة الحالية: نجحت مع Dio وRetrofit، وتشمل عمليات التوليد والإدارة والإصلاح.
- عقود البيانات المخصصة: نجحت مع Dio وRetrofit، مع اختبار Entity بديلة ودالة تحويل مخصصة وإصلاح ملف Use Case مفقود والمحافظة على Models.
- نسخة المتجر: نجح Doctor، وإضافة عملية بــProductsEntity وأخرى بــUsersEntity، ثم نجحت اختبارات المتجر الـ19.
- بناء النكهات: تسعة عمليات بناء ناجحة، وتشغيل نكهات iOS الثلاث على المحاكي.
- فحص النشر التجريبي: تحذير واحد بسبب التغييرات غير المسجلة في Git؛ لم تُنشر الحزمة.

توقفت محاولة Android الأولى بمهلة إعداد/بناء Gradle، ثم نجحت المحاولة التالية. وتوقفت محاولة Retrofit في جلب الحزم قبل التحقق، ثم نجحت إعادة الحالة منفردة. حدث كذلك timeout لاختبار وحدة أثناء تشغيل عدة عمليات SDK ثقيلة؛ أعيدت المجموعة بعد انتهاء الحمل ونجحت اختبارات الأداة الـ182. أُبقي سياق إعادة المحاولة في سجلات العقود لتوثيق النتائج دون إخفاء الإخفاقات المؤقتة.

**الأدلة والتوثيق**

- result.json: ملخص النتائج والأرقام.
- unit_tests.log وanalyze.log: فحص الأداة.
- generated_apps.log: مصفوفة التطبيقات المولّدة.
- contracts_dio_and_retry_context.log وcontracts_retrofit_final.log: العقود الجديدة ونتائج إعادة الاختبار.
- native_android.log وnative_ios.log وnative_macos.log: بناء النكهات وتشغيل iOS.
- native_identifiers.json: معرفات الحزم المستخرجة من المخرجات الفعلية.
- store_upgrade.log: التحقق على نسخة المتجر.
- resolver_portability.log: التحقق من غياب أي مسارات staging/cache في حل الحزم بعد تطبيق العمليات وتنظيف مساحة التحقق.
- package_dry_run.log: فحص الحزمة دون نشر.
