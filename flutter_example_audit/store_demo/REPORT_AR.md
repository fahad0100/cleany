# تجربة CLEANY المحلية على تطبيق Flutter فعلي

المشروع: `flutter_example`، اسم حزمة التطبيق: `cleany_store`، اسم العرض: **Cleany Store**.

تم إنشاء تطبيق يتصل فعلًا بخدمة [Fake Store API](https://fakestoreapi.com/)، واستخدام نسخة CLEANY الموجودة في المستودع عبر `path: ..`، ثم تخصيص الأكواد المولّدة لتناسب عقد الخدمة الحقيقي. لم تُعدّل ملفات مكتبة CLEANY في هذه المهمة.

## ما نُفّذ بواسطة CLEANY

استُخدمت القائمة التفاعلية فعليًا؛ السجلات محفوظة داخل `logs/`، وسجل العناصر النهائي داخل `../../flutter_example/.cleany/features.json`.

| العملية | النتيجة |
| --- | --- |
| Initialize project | إنشاء App وCore وDI وRouter والإعدادات والترجمة الرسمية ونقاط تشغيل البيئات |
| Create feature | `products` باستخدام Cubit، و`carts` باستخدام Bloc، و`users` و`auth` باستخدام Cubit |
| Create component | `product_card` و`status_panel` دون حالة، و`quantity_stepper` مع Cubit |
| Add use case | ست عمليات مرتبطة بالميزات الموجودة، موضحة أدناه |
| List features / components | التحقق من ظهور الميزات الأربع والمكونات الثلاثة في السجل والقائمة |

| الميزة | حالات الاستخدام الإضافية التي وُلّدت عبر CLI | الربط الفعلي بعد التخصيص |
| --- | --- | --- |
| products | `get_featured_product` | جلب المنتج المميز من `GET /products/1` |
| carts | `create_cart` | طلب بمعرف المنتج والكمية والمستخدم إلى `POST /carts` |
| carts | `delete_cart` | حذف بالمعرف عبر `DELETE /carts/{id}`، بنتيجة void |
| users | `get_user_profile` | جلب الملف المحدد عبر `GET /users/{id}` |
| auth | `sign_in` | إرسال اسم المستخدم وكلمة المرور إلى `POST /auth/login` |
| auth | `sign_out` | مسح الجلسة المحلية؛ لا يُفترض وجود endpoint غير متاح للخروج |

حالات الجلب الأساسية `GetProducts` و`GetCarts` و`GetUsers` و`GetAuth` موجودة كذلك. حالات الاستخدام تشترك في Repository متماسكة لكل ميزة بدل توليد Repository منفصلة لكل عملية.

## حدود التوليد والتخصيص

CLEANY ولّدت الهيكل والتسجيلات والتوصيلات الأولية. لا يُنسب إليها توليد التطبيق النهائي تلقائيًا من رابط API وحده.

جرى تخصيص ما يلي في تطبيق المثال:

- تحويل نتائج المنتجات والسلال والمستخدمين إلى قوائم Entities بدل قالب العنصر المفرد.
- إضافة Models تعكس حقول `rating` و`name` و`address` ومنتجات السلة المتداخلة.
- إضافة معاملات فعلية لحالات الاستخدام: معرف المستخدم، معرف المنتج، الكمية وبيانات الدخول.
- توصيل Data hooks التي يولّدها أمر Add use case بالخدمة الفعلية.
- بناء واجهات المتجر والتنقل والبحث والتصفية والترتيب ونوافذ التفاصيل والعربية وRTL.
- إضافة الجلسة المؤقتة والاختبارات.

نسخة ما قبل التخصيص محفوظة في `generated_scaffold/`. وملف `scaffold_comparison.json` يفرّق بين الملفات الأصلية، والملفات المولّدة التي خُصصت، والملفات التي أضيفت للتطبيق. ملفات البناء الناتجة عن Freezed وRetrofit مستثناة من هذه المقارنة المصدرية.

## طريقة عمل التطبيق

1. صفحة المنتجات تجلب المنتجات الفعلية وصورها، وتتيح البحث والتصنيف والترتيب بالسعر. المنتج المميز يستخدم حالة الاستخدام الإضافية.
2. نافذة المنتج تعرض التفاصيل والسعر، وتستخدم مكوّن `quantity_stepper` لتحديد كمية من 1 إلى 99.
3. إنشاء سلة يرسل طلبًا حقيقيًا للخدمة، ثم يعرض معرف السلة والمنتجات والإجمالي.
4. صفحة السلال تجلب السلال العامة. تجمع طبقة Domain بيانات المنتجات والسلال عبر عقود مستقلة لعرض الاسم والصورة والسعر؛ طبقات Data لا تعتمد على بعضها.
5. صفحة المستخدمين تعرض بيانات الحسابات العامة، وتفتح ملف المستخدم بطلب مستقل. لا تحتوي Entity المستخدم على كلمة مرور.
6. صفحة الحساب تتيح تعبئة حساب التجربة العام، وتختبر الدخول الصحيح والخاطئ. يحتفظ التطبيق بالجلسة في الذاكرة فقط، وينظفها عند الخروج.
7. زر اللغة يبدل بين الإنجليزية والعربية مع اتجاه RTL، عبر `flutter_localizations` وملفات ARB.

**الخدمة تجريبية:** الإضافة والحذف في Fake Store محاكاة ولا يغيران مجموعة بيانات الخادم بشكل دائم. لهذا تظهر السلة الجديدة محليًا، ويخفي الحذف الناجح السلة من العرض الحالي، وقد تعود البيانات الأصلية بعد التحديث. هذا موضح داخل التطبيق. انظر [وثائق المشروع المصدر](https://github.com/keikaavousi/fake-store-api).

## المعمارية وجودة الفصل

- `data/datasources`: JSON خام من Retrofit، دون تحويل إلى Entity أو معالجة Failure.
- `data/models`: شكل JSON الفعلي باستخدام Freezed وJSON serialization.
- `data/repositories`: تحويل JSON إلى Model ثم Entity، مع حد واحد لتحويل الأخطاء إلى `Failure` وإرجاع `multiple_result`.
- `domain`: عقود ومستويات استخدام مستقلة عن Dio وRetrofit وFlutter. التحقق من صحة الطلب وتركيب معلومات السلة في هذه الطبقة.
- `presentation`: Entities وحالات واضحة للتحميل والنجاح والفشل، مع حالة مستقلة لكل عملية إضافية.
- `app`: نقطة تركيب مركزية تدير خدمات التطبيق وعمرها، وتوفر Controllers كـ factories يملكها `BlocProvider`.
- `components`: ملفات Widget مباشرة داخل مجلد المكوّن، وحالة Cubit في مجلد شقيق؛ لا يوجد مجلد widgets إضافي.

هذه بنية مناسبة لتطوير تطبيق تجريبي حقيقي والعمل على كل ميزة بصورة مستقلة. لا يعني نجاح الفصل وحده اكتمال متطلبات متجر إنتاجي.

## الفحوص المنفذة

البيئة: Flutter **3.47.7** وDart **3.13.5**، ومحاكي **iPhone 17 Pro / iOS 26.5** بالمعرف `189091C8-6638-4DAD-94BA-0C39D8BB606C`.

| الفحص | النتيجة |
| --- | --- |
| تثبيت CLEANY من المسار المحلي وتوليد عناصرها | اكتمل، مع توثيق سجل كل عملية |
| توليد الترجمة وFreezed وJSON وRetrofit | اكتمل |
| التحليل الساكن للتطبيق والاختبارات | دون ملاحظات في الفحص النهائي |

| رحلة UI مع API الحقيقية على iPhone | نجحت، مع حفظ صور الواجهات |

تشمل الاختبارات الحتمية: تحويل القوائم والحقول المتداخلة، تطابق الطلبات ومعاملاتها، تركيب السلال، رفض الكميات والمعرفات غير الصحيحة قبل الشبكة، تسجيل الدخول والخروج، أخطاء الشبكة والاستجابة غير الصحيحة، حماية Result من استثناء المراقب، حصر إرسال Token في أصل الخادم الموثوق، حالات Cubit وBloc، وحدود مكوّن الكمية وإغلاق Controllers.

اختبار التكامل الحي يتحقق من: 20 منتجًا، البحث، فتح التفاصيل، زيادة الكمية، إنشاء سلة وعرضها، حذفها، جلب السلال العامة، فتح ملف مستخدم، رفض كلمة مرور خاطئة، قبول حساب التجربة، الخروج، ثم التحويل إلى العربية وRTL. سجلات القيادة قد تعرض فحوص إنهاء داخلية إضافية؛ المقصود هنا رحلة تكامل واحدة كاملة، وليس الادعاء بوجود عدة رحلات مستقلة.

الـFixtures ومحوّل النقل البديل خاصان باختبارات الوحدة فقط. التطبيق واختبار التكامل لا يستخدمانهما كبديل للخدمة الفعلية.

## ما كُشف أثناء التجربة وعولج

1. توقفت محاولة توليد بسبب تغير مدخلات المشروع أثناء التحقق، دون تطبيق الخطة. لم يُحسم مصدر التغيير. أُعيدت العمليات منفردة مع فحص السجل، واكتمل التوليد. تسلسل الإجابات المسبق في المحاولة الأولى تداخل مع مطالبة إعادة المحاولة؛ السجل الأول يحفظ المحاولات الملغاة، وسجلات العمليات المنفردة توثق النجاح النهائي.
2. استجابات قوائم Fake Store لا تناسب قالب العنصر المفرد الافتراضي؛ جرى تخصيص العقود وModels وحالات Presentation.
3. مع Retrofit الحالي، استعمال Map بقيمة `dynamic` ضمن هذه العقود ولّد تحويلًا غير مناسب. استُخدمت أنواع JSON خام مناسبة (`Object?`) وتحويلات واضحة داخل Data، وأعيد توليد الملفات؛ التحليل النهائي سليم.
4. حذف سلة غير محفوظة يعيد HTTP 200 مع JSON `null`. جرى اعتماد نتيجة void للحذف، واختبارها باستجابة null بدل فرض جسم استجابة غير موجود.
5. ضُبطت محددات اختبار UI لتفريق نص الملف الشخصي عن النص نفسه في القائمة، والتحقق من Widget العداد مباشرة. هذه كانت مشكلات محددات الاختبار، وليست أخطاء حساب الكمية أو بيانات الملف.
6. جرى جعل تفاصيل المستخدم قابلة للتمرير، وإخفاء رسالة الصفحة السابقة عند تبديل التبويب.

## حدود التجربة والتحسينات التالية

- اختُبر iOS على المحاكي؛ لم يُنفّذ اختبار Android أو بناء إصدار موقع للنشر.
- أُنشئت إعدادات DEV/UAT/PROD وFlavorizr، لكن لم تُطبّق مولدات النكهات الأصلية على المنصات في هذه المهمة. التشغيل الحالي يستخدم نقاط الدخول دون `--flavor`.
- الخدمة لا توفر سلة إنتاجية أو دفعًا أو مخزونًا متزامنًا. تطوير متجر فعلي يحتاج Backend مناسبًا وعقود أعمال مخصصة.
- الجلسة مقصودة أن تكون مؤقتة. حفظ تسجيل الدخول مستقبلًا يحتاج استراتيجية صلاحية وتجديد وحفظ آمن تتوافق مع خادم حقيقي.
- جميع القوائم صغيرة؛ لم تُختبر pagination أو أحجام بيانات كبيرة، ولم تُنفّذ قياسات أداء تثبت رقمًا معينًا.
- حالات الاستخدام الجديدة ذات معاملات الطلب ونتائج القوائم والـModels المتداخلة احتاجت تخصيصًا بعد CLI. دعم تعريف هذه العقود داخل الأداة سيكون تحسينًا مفيدًا لتقليل العمل اليدوي.

حُفظت محتويات مجلد المثال السابقة في `../before_fake_store_20261101_141141/` قبل إنشاء التطبيق، لتجنب فقدان أعمال التجارب السابقة.
