# تقرير اختبار إضافة Use Case داخل flutter_example

التاريخ: 31 أكتوبر 2026.

تم اختبار الإضافة من CLI فعليًا داخل المشروع `test_cleany_project` في `flutter_example`، باستخدام اعتماد Cleany المحلي `path: ..`. اجتازت الإضافة الحالات المختبرة دون الحاجة إلى تغيير تنفيذ الأداة.

## نتيجة التوليد عبر القائمة

| الميزة | إدارة الحالة | اسم Use Case | النتيجة | التوليد والتحقق |
| --- | --- | --- | --- | --- |
| home | Cubit | refresh_home | HomeEntity الحالية | ناجح — 28 ثانية |
| home | Cubit | clear_home | void | ناجح — 27 ثانية |
| catalog | Bloc | refresh_catalog | CatalogEntity الحالية | ناجح — 27 ثانية |
| catalog | Bloc | clear_catalog | void | ناجح — 29 ثانية |

تم اختيار 13 من القائمة، ثم الميزة والاسم ونوع الإرجاع، ثم Apply and validate في كل مرة. شغّلت كل معاملة جلب الاعتماديات وتوليد الترجمة وFreezed وتحليل Flutter قبل تطبيق الملفات. القائمة عرضت الميزات الثلاث فقط واستبعدت المكونات.

## التحقق من الملفات والربط

- أُضيفت لكل عملية ملفات Use Case وعقد Repository في Domain وتنفيذ Repository في Data.
- عمليات Entity تستخدم Model الموجودة وتحولها إلى Entity الموجودة داخل Repository. تحقق الاختبار من حقول Home الثلاثة: id وtitle وvisits، ومن Entity الخاصة بـCatalog.
- عمليات void تنتظر اكتمال مصدر البيانات وتعيد Result<void, Failure> دون محاولة قراءة Entity من الاستجابة.
- حدث الربط تلقائيًا في ملف DI المركزي، مع الاحتفاظ بمصانع المتحكمات. تحقق التشغيل من وصول العمليات الأربع إلى Cubit وBloc عبر GetIt.
- أُضيفت حقول حالة مستقلة لكل عملية، وأحداث Bloc المناسبة. بقيت حالات التحميل والنجاح والفشل الأصلية للميزة متوافقة مع الصفحات الحالية.
- سُجلت ملكية ملفات العمليات وملف حالة العمليات المشترك ومخرجات Freezed في السجل.
- قارنت 28 ملفًا قبل التوليد وبعده باستخدام SHA-256. بقيت Entity وModel ومخرجاتهما وصفحات الميزات وواجهات Retrofit والمسارات وتركيب الصفحات وpubspec مطابقة للأصل بايتًا ببايت.

أثبتت اختبارات الإضافة: تحميل ثم نجاح Entity أو void، وتحويل الأخطاء إلى Failure، وإبقاء أخطاء الأعمال كما هي، والتعامل مع JSON غير صالح، وإمكانية إعادة المحاولة. كما أثبتت استقلال حالات العمليات المتزامنة، وبقاء حالاتها أثناء تحميل الميزة الأساسي، ومنع تكرار الاستدعاء الجاري، وتجاهل اكتمال Cubit المتأخر بعد إغلاقه. فشل مراقب تسجيل الأخطاء لا يخرج عن Result في تنفيذ العمليات الجديدة.

على المحاكي اختُبرت العمليات الأربع من خلال واجهة اختبار تظهر حالتها، ثم اختُبرت نقاط الربط الأصلية غير الموصّلة. اجتازت سيناريوهات التطبيق السابقة أيضًا اختبارات HTTP المحلي والتنقل وBloc واللغة العربية واتجاه RTL والمكونات.

بعد الفحوص أُعيد تشغيل التطبيق العادي ببيئة dev على المحاكي، وظهرت صفحة Home ونتيجة الخادم المحلي CLEANY_LOCAL_OK. [صورة التشغيل](use_case_app.png) · [سجل التشغيل](logs/use_case_app_launch.log).

## ملاحظة عن API

نقاط الربط في Data ما زالت تحتاج عقد الخادم كما طُلب. لم يفترض التوليد endpoint أو HTTP method. أثبت الاختبار أن استدعاء العمليات الأربع كما وُلدت يعيد Failure، مع صفر طلبات HTTP من هذه العمليات.

اختبارات النجاح تستخدم مصادر بيانات متحكمًا بها داخل الاختبارات، مع تشغيل التنفيذ المولّد الحقيقي من Repository إلى Use Case ثم Cubit/Bloc. توصيل API الفعلي هو خطوة التطبيق التالية. صفحات الميزة الحالية لا تعرض حالات العمليات الإضافية تلقائيًا؛ يمكن للواجهة مراقبة refreshHomeStatus أو clearHomeStatus، ونظائرهما في Catalog.

## إعادة تشغيل الفحوص

من مجلد flutter_example:

```sh
flutter analyze --no-pub
flutter test --reporter expanded
flutter test integration_test -d 189091C8-6638-4DAD-94BA-0C39D8BB606C --flavor dev --dart-define=API_BASE_URL=http://127.0.0.1:8787 --reporter expanded
```

اختبارات التكامل السابقة تحتاج خادم الاختبار المحلي على المنفذ 8787. ملفه: [mock_api_server.py](mock_api_server.py).

للتجربة اليدوية شغّل `dart run cleany` من مجلد المثال ثم اختر 13. الأسماء الأربع الموجودة ستُرفض إذا أُعيد إدخالها، ويمكن اختيار اسم جديد. استدعاء Cubit: `context.read<HomeCubit>().refreshHome()`، واستدعاء Bloc: `context.read<CatalogBloc>().add(const CatalogEvent.refreshCatalogRequested())`.
